# 业主端 App 低保真原型图（UI / UX）

> 说明  
> 1. 本文档只服务 `业主客户端 App 的 UI / UX 重构`。  
> 2. 不删减任何既有业务需求，所有功能仍以主 PPT、既有 PRD、积分与志愿服务闭环为准。  
> 3. 本文档的作用，是让研发明确：`每一页该怎么排、首屏先看到什么、按钮放哪里、用户怎么走`。  
> 4. 这是低保真原型，不定义最终视觉稿，但定义页面结构、层级、主操作和状态表达。  

---

## 一、设计目标

这不是一个“把功能摆上去”的网页，而是一个 `用户愿意点、愿意继续看、愿意真的完成处理动作` 的移动端伪 App。

业主端 UI / UX 要同时满足 4 个目标：

1. 用户一打开就知道 `现在最该做什么`
2. 用户能快速比较 `哪种处理方式最省心`
3. 用户在每一步都能看到 `我已经推进了多少`
4. 用户愿意反复打开，因为这里有 `进度、奖励、成果、参与感`

---

## 二、导航结构

底部导航固定 5 个入口：

1. `首页`
2. `志愿`
3. `消息`
4. `家人`
5. `我的`

对应职责：

- `首页`：当前事件、推荐动作、处理进度
- `志愿`：任务大厅、成果墙
- `消息`：办理提醒、到账提醒、成果提醒
- `家人`：代办关系、同步状态、适老辅助
- `我的`：积分账户、权益、等级、历史记录

---

## 三、全局布局规范

### 3.1 页面通用骨架

```text
+--------------------------------------------------+
| 状态栏 / 安全区                                   |
| 页面标题                    右侧功能/提醒/更多      |
+--------------------------------------------------+
| 页面主内容（滚动区）                               |
|                                                  |
|                                                  |
|                                                  |
+--------------------------------------------------+
| 首页 | 志愿 | 消息 | 家人 | 我的                  |
+--------------------------------------------------+
```

### 3.2 交互原则

1. 首屏只突出一个主任务
2. 每屏只放一个主 CTA
3. 卡片优先于大段文字
4. 先给结论，再给解释
5. 所有状态都要有反馈：`已锁定 / 待到账 / 已到账 / 已完成 / 待确认`

### 3.3 组件风格要求

- 状态卡：首屏最大视觉焦点
- 动作卡：可点击、强对比、强按钮
- 进度条：像订单进度，不像说明列表
- 账户卡：像资产页，不像规则页
- 任务卡：像本地生活任务大厅，不像通知公告

## 四、页面 1：首页（任务处理首页）

### 4.1 页面目标

让用户在 5 秒内回答 4 个问题：

1. 发生了什么
2. 为什么会提醒我
3. 推荐我怎么做
4. 我点下去以后会发生什么

### 4.2 信息层级

1. 顶部事件状态卡
2. 推荐方案卡
3. 其他处理方式
4. 当前进度
5. 当前奖励状态

### 4.3 低保真原型

```text
+--------------------------------------------------+
| 楼道提醒                               铃铛 头像   |
+--------------------------------------------------+
| [状态总卡]                                        |
| 红色风险 / 3号楼2单元502                         |
| 旧鞋柜与纸箱占用楼道，需要尽快处理                |
| 截止：24小时内完成首轮推进                         |
| 当前状态：等待你确认处理方式                        |
+--------------------------------------------------+
| [推荐动作卡 - 高亮]                               |
| 推荐方案：申请周转位                               |
| 适合你：家里物品较多，先挪走再慢慢清理              |
| 预计耗时：2分钟提交，48小时内完成处理               |
| 本次收益：待到账 30住户积分 + 食用油兑换券          |
| 点击后会发生：物业预留周转位，并同步后续协助         |
|                     [立即申请]                     |
+--------------------------------------------------+
| [次级动作卡] 预约回收                              |
| 预计耗时 1分钟 | 适合可直接交回收物                 |
|                     [选择这个方案]                  |
+--------------------------------------------------+
| [次级动作卡] 预约清运                              |
| 预计耗时 1分钟 | 适合需要上门搬运                   |
|                     [选择这个方案]                  |
+--------------------------------------------------+
| [次级动作卡] 今晚自己处理                           |
| 预计耗时 30分钟 | 回访确认后奖励到账                 |
|                     [登记自己处理]                  |
+--------------------------------------------------+
| [进度卡]                                          |
| 已巡查发现  ->  已温和提醒  ->  等你选择方案  -> ... |
+--------------------------------------------------+
| [奖励提示卡]                                      |
| 本次奖励已锁定：待到账 30积分 + 1张兑换券           |
| 到账条件：按时完成本次闭环                         |
+--------------------------------------------------+
| 首页 | 志愿 | 消息 | 家人 | 我的                  |
+--------------------------------------------------+
```

### 4.4 研发要求

- 首屏不能先出现“模块列表”
- 推荐方案卡必须是最大主卡
- 次级方案做成可比较卡片，不要做成纯按钮列表
- 每个动作卡必须固定显示：
  - `适合谁`
  - `预计耗时`
  - `本次收益`
  - `点击后会发生什么`

## 五、页面 2：方案确认页 / 底部抽屉

### 5.1 页面目标

在用户点击动作卡后，用最短路径完成确认，不再让用户读很多说明。

### 5.2 低保真原型

```text
                [底部抽屉弹出]
+--------------------------------------------------+
| 申请周转位                                        |
|--------------------------------------------------|
| 你将获得：                                        |
| - 48小时周转位                                    |
| - 物业后续协助                                    |
| - 待到账 30住户积分                               |
| - 闭环后可领取兑换券                              |
|                                                  |
| 接下来会发生：                                    |
| 1. 系统同步生成处理记录                            |
| 2. 物业确认周转位                                  |
| 3. 如有需要可安排后续协助                           |
|                                                  |
| [取消]                        [确认申请]          |
+--------------------------------------------------+
```

### 5.3 研发要求

- 动作确认用 `底部抽屉`，不要跳生硬新页
- 抽屉信息只保留结果型信息，不讲长规则
- 确认后要立即给用户成功反馈

## 六、页面 3：提交成功 / 处理中状态页

### 6.1 页面目标

把“我刚刚点了一个按钮”转成“事情已经真的往前走了”。

### 6.2 低保真原型

```text
+--------------------------------------------------+
| 处理进度                                          |
+--------------------------------------------------+
| [成功状态卡]                                      |
| 已为你提交：申请周转位                             |
| 当前状态：等待物业确认                             |
| 预计下一步：2小时内完成分配                        |
|                                                  |
|                [查看进度]                          |
+--------------------------------------------------+
| [时间线]                                          |
| 刚刚 你已提交周转位申请                            |
| 刚刚 系统已同步给物业中台                          |
| 待处理 物业确认周转位                              |
| 待处理 上门协助/后续清运                           |
+--------------------------------------------------+
| [奖励状态卡]                                      |
| 已锁定奖励：30住户积分 + 兑换券                    |
| 当前状态：待到账                                  |
+--------------------------------------------------+
```

### 6.3 研发要求

- 提交后必须有成功态，不要无反馈地回首页
- 成功态里要明确 `下一步是谁处理`
- 同时展示 `进度变化` 和 `奖励变化`

## 七、页面 4：进度详情页（订单式）

### 7.1 页面目标

做成“像订单履约页”的感觉，让用户持续回来查看。

### 7.2 低保真原型

```text
+--------------------------------------------------+
| 本次处理进度                                      |
+--------------------------------------------------+
| [顶部进度条]                                      |
| 已提醒 -> 已选择方案 -> 已分配 -> 处理中 -> 已闭环 |
+--------------------------------------------------+
| [当前节点大卡]                                    |
| 当前在办：物业正在确认周转位                       |
| 预计完成：今天 16:00 前                            |
| 你现在无需额外操作                                 |
+--------------------------------------------------+
| [时间线列表]                                      |
| 14:08 你已申请周转位                               |
| 14:08 系统同步给物业中台                           |
| 15:00 物业已分配周转位                             |
| 15:30 志愿者/服务协助已安排                        |
| 待完成 回访确认并奖励到账                           |
+--------------------------------------------------+
| [底部提示]                                        |
| 奖励会在本次事件闭环后自动到账                     |
+--------------------------------------------------+
```

### 7.3 研发要求

- 不能只是普通 timeline，要有“当前节点高亮”
- 必须出现 “你现在还需要做什么 / 不需要做什么”
- 这页是高频回看页，要尽量克制说明文字

### 8.2 信息层级

1. 适合你的任务
2. 就近任务
3. 已报名 / 已完成
4. 成果墙入口

### 8.3 低保真原型

```text

+--------------------------------------------------+

| 适合你：熟悉手机操作，可快速协助                    |
| 完成后会进入楼栋成果墙                              |
|                    [报名这个任务]                  |
+--------------------------------------------------+
| [任务卡]                                          |
| 陪同完成一次楼道清理协助                            |
| 协助任务 | 30分钟 | +25贡献积分                    |
```

## 十三、关键交互流

### 13.1 用户处理事件主链路

```text
首页看到提醒
  -> 点击推荐方案
  -> 底部抽屉确认
  -> 成功态
  -> 进度详情
  -> 事件闭环
  -> 奖励到账
  -> 资产页看到变化
```

### 13.2 用户参与志愿主链路

```text
志愿页看到适合自己的任务
  -> 报名任务
  -> 等待中台确认
  -> 完成任务
  -> 贡献积分到账
  -> 成果墙出现新成果
  -> 资产页与消息页同步反馈
```

## 十五、交付给研发的落地要求

研发实现时，不要把这里理解成“再加页面”，而是把现有需求重新组织成以下形态：

1. 首页像 `任务处理入口`
2. 进度页像 `订单履约页`
3. 资产页像 `账户系统`
4. 志愿页像 `任务大厅`
5. 家人页像 `关系与代办页`
6. 消息页像 `真实 App 消息中心`

最终标准不是“模块都有了”，而是：

- 用户愿意点
- 用户点完知道发生了什么
- 用户能感受到推进
- 用户愿意回来继续看
